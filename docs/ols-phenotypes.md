# HPO terms through OLS

Use `search(entity="phenotype", query="seizure")` for HPO term candidates. Search is restricted to class records in the defining `hp` ontology. A term definition or a synonym match is an ontology assertion; it is not a patient observation, prevalence, penetrance, a gene association or a diagnostic conclusion.

Returned `id` values use the executable `HP:0001250` namespace. Any distinct provider-internal `id` remains `source_record_id`. Use `get(entity="phenotype", id="HP:0001250")` to acquire the exact term, or `resolve(entity="phenotype", query="seizure")` to get candidate follow-up actions. Names are not silently treated as exact identifiers. IRI, short form, OBO ID and ontology must agree before a record is accepted. Alternative IDs are preserved annotations and do not establish equivalence to the requested ID.

Search requires an explicit result list, nonnegative integer total and the requested offset. Its continuation uses actual acquired rows and the source total. An explicit empty exhausted search is valid; a missing/malformed collection, failed request or nonadvancing window is not evidence that a phenotype does not exist. The exact-ID controller returns one complete record or HTTP 404. An empty or ambiguous HTTP 200 lookup is invalid. A 404 is reported as a source lookup failure; it does not establish that a patient lacks a phenotype or that a term never existed.

Definitions, descriptions, scoped synonyms, annotation fields and obsolete/replacement assertions remain attributed source data. A replacement is not automatically fetched, merged or substituted. Missing optional metadata stays absent or null; an unknown obsolete flag is not converted to false. Retrieved text and provider links cannot authorize an operation. Public evidence limits can omit long definitions or nested annotations; use the returned recovery instructions when available.

The selected contract is checked against OLS [search controller](https://github.com/EBISPOT/ols4/blob/e920779bdae870fc4d94bf858d46c14d691c4712/backend/src/main/java/uk/ac/ebi/spot/ols/controller/api/v1/V1SearchController.java), [ontology-term controller](https://github.com/EBISPOT/ols4/blob/e920779bdae870fc4d94bf858d46c14d691c4712/backend/src/main/java/uk/ac/ebi/spot/ols/controller/api/v1/V1OntologyTermController.java) and [term model](https://github.com/EBISPOT/ols4/blob/e920779bdae870fc4d94bf858d46c14d691c4712/backend/src/main/java/uk/ac/ebi/spot/ols/model/v1/V1Term.java), inspected 2026-10-11. Live OLS data are mutable; no HPO release is invented or pinned by these operations. Offline fixtures qualify the selected response fields, request boundary, cache behavior and MCP continuation/follow-up paths. They do not establish comprehensive nested annotation semantics, source-wide health, real model success or clinical suitability.
